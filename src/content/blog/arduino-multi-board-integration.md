Smart Parking 팀 프로젝트의 초기에는 각자 PC에서 서버를 실행하고 개별 Arduino를
테스트했습니다. 이후 Arduino 다섯 대를 하나의 서버에 연결하고, 입차부터 주차와 출차까지
전체 흐름을 시연하는 구성으로 통합했습니다.

이 글은 그 과정에서 직접 참여한 **보드별 장치 식별자 설정과 펌웨어 업로드 작업**을
중심으로 정리한 회고입니다. 서버의 장치 식별과 명령 처리 설명은 팀 최종 코드를 확인해
덧붙였습니다. 프로젝트 기간은 2026년 8월 13일부터 8월 28일까지입니다.

## 출발점: 각자의 PC에서 개별 보드 테스트

초기 테스트에서는 팀원마다 자신의 PC에서 로컬 서버를 실행하고, 각자 연결한 보드의
동작을 확인했습니다. 당시 펌웨어에는 동일한 장치 식별자가 하드코딩되어 있었고,
여러 보드를 하나의 서버에 연결하는 구성을 아직 고려하지 않은 상태였습니다.

개별 환경에서 확인하던 보드들을 하나의 시스템으로 묶으려면, 서버가 어느 보드에서
온 상태인지 구분하고 명령도 해당 보드에 전달할 수 있어야 했습니다.

| 항목 | 초기 개별 테스트 | 통합 구성 |
| --- | --- | --- |
| 서버 | 팀원별 PC에서 각각 실행 | 하나의 서버에 다섯 대 연결 |
| 장치 식별 | 동일한 식별자를 사용한 시험용 펌웨어 | 보드마다 서로 다른 `DEVICE_ID` 설정 |
| 동작 확인 | 개별 보드 중심 | 입차·주차·출차의 전체 흐름 시연 |

## 보드마다 DEVICE_ID 설정하기

최종 펌웨어에서는 장치 식별자를 `DEVICE_ID`로 정의합니다. 예를 들어 P1 보드의
스케치에는 다음 설정이 있습니다.

```cpp
#define DEVICE_ID "P1"
```

*팀 최종 저장소의 [p1.ino 설정](https://github.com/pi-lee-lee/team/blob/main/%EA%B3%BC%EC%A0%9C/1/release/ardu/p1/p1.ino#L21)에서 발췌했습니다.*

`P1`부터 `P5`까지는 접속 순서대로 자동 부여되는 번호가 아니라, 보드별 스케치에
설정한 값입니다. 각 보드의 역할과 식별자는 다음과 같이 대응합니다.

| 장치 식별자 | 담당 장치 |
| --- | --- |
| `P1` | 주차 공간 A1~A3와 입구 센서 |
| `P2` | 주차 공간 A4~A5와 출구 센서 |
| `P3` | 입구 차단봉의 서보모터 |
| `P4` | 출구 차단봉의 서보모터 |
| `P5` | 주차 공간 안내등의 릴레이 |

통합 과정에서 이 식별자들을 서로 다르게 설정한 펌웨어를 각 Arduino에 업로드했습니다.
공통 코드를 사용하는 보드들이어도, 실제로 어느 보드에 어떤 설정을 올리는지 구분하는
작업이 필요했습니다.

## 서버는 장치를 어떻게 구분하는가

식별자 설정이 통신에서 어떻게 사용되는지도 팀 최종 코드를 따라 확인했습니다.
다음은 서버 구현을 읽고 정리한 흐름입니다.

1. 보드는 `S` 상태 프레임에 자신의 `DEVICE_ID`를 포함합니다.
2. 서버는 체크섬 검사를 통과한 `S` 프레임에서 장치 식별자를 읽습니다.
3. 명령을 보낼 때는 장치 식별자와 모듈 이름으로 대상을 찾고, 그 보드에 해당하는
   연결을 사용합니다.

관련 코드는 Arduino의 [상태 프레임 생성](https://github.com/pi-lee-lee/team/blob/main/%EA%B3%BC%EC%A0%9C/1/release/ardu/p1/Modules.h#L315),
서버의 [장치 식별자 추출](https://github.com/pi-lee-lee/team/blob/main/%EA%B3%BC%EC%A0%9C/1/release/server/nodes.h#L18),
[명령 대상 조회](https://github.com/pi-lee-lee/team/blob/main/%EA%B3%BC%EC%A0%9C/1/release/server/downlink.h#L393)에서 확인할 수 있습니다.

코드를 읽을 때 비슷해 보이는 식별자들의 역할도 구분했습니다.

| 이름 | 구분하는 대상 |
| --- | --- |
| `DEVICE_ID` | 보드 펌웨어에 설정한 장치 식별자 |
| `devid` | 서버에서 관리하는 장치 식별자 |
| 모듈 이름 | 특정 보드에 연결된 센서나 액추에이터 |
| `rid` | 명령과 응답을 대응시키는 요청 번호 |

예를 들어 어느 보드의 어느 모듈에 명령을 보낼지 찾는 일과, 보낸 명령에 대한 응답을
대응시키는 일은 별도로 다룹니다. 보드에 설정한 `DEVICE_ID`가 서버의 대상 조회까지
이어지는 구조입니다.

## 다섯 대를 연결한 최종 시연

최종 모형에서는 Arduino·ESP-01 장치 다섯 대를 단일 서버에 연결하고, 하나의 전원 공급원으로
구동했습니다. 보드의 센서 입력과 서버 판단, 안내등과 차단봉 동작이 연결된 상태에서
입차·주차·출차의 전체 흐름을 시연했습니다.

최종 시연에서는 전체 흐름이 원활하게 동작했고, 차단봉 서보모터의 떨림도 나타나지 않았습니다.
서보 제어 신호 안정화에 관한 참여 내용은 연결된 프로젝트 상세 페이지에 별도로 정리했습니다.

![주차 공간 다섯 곳, LCD와 안내등, 입출구 차단봉을 갖춘 스마트 주차장 모형](../../assets/projects/smart-parking/hardware-front.jpg)

*팀 발표자료에 포함된 실제 제작 모형입니다.*

구현한 범위는 실제 하드웨어를 연결한 주차장 모형입니다. 실제 주차장 현장에 설치하거나
운영한 단계는 아닙니다.

## 정리

이번 통합 작업의 핵심은 각자 테스트하던 보드들을 하나의 서버에서 구분할 수 있도록
설정을 맞추고, 해당 설정을 반영한 펌웨어를 각 보드에 업로드하는 일이었습니다.

보드 수가 늘어날 때는 소스 코드뿐 아니라 **장치의 역할, 식별자, 업로드한 펌웨어의 대응 관계**도
함께 관리해야 합니다. 또한 개별 보드의 동작 확인과 여러 보드가 연결된 전체 흐름의 확인을
각각 진행할 필요가 있습니다.

전체 프로젝트의 구조와 나의 참여 범위는 아래의 ‘Arduino 기반 스마트 주차장’ 페이지에 정리했습니다.
